## 17. Обязательные правки к основному ТЗ (Must)

### 17.1 Блок `key_pool.py` / `jobs.py`: лог сторожа (G2)

`gemini_pool.reap_stale()` возвращает не только имена, а пары `(name, ttl_s)`; **для обратной совместимости** добавить новый метод `reap_stale_detailed() -> List[Tuple[str, float]]`, а `reap_stale()` оставить и вернуть те же имена. `jobs._watchdog_tick` использует детальный вариант; функция `gemini_pool_lease_ttl()` остаётся (возвращает `KEY_LEASE_TTL`) для совместимости импортов.

### 17.2 Контракт импортов (G3)

После этапа E4 из `ocr_service/jobs.py` должны по-прежнему импортироваться без ошибок:
`JOBS, JOB_TASKS, JOB_MAX_SECONDS, JOB_RESULT_TTL_SECONDS, spawn_job, _job_queue_metrics, _job_public_payload, _cleanup_expired_jobs, _watchdog_tick, start_cleanup_loop, stop_cleanup_loop, start_watchdog, stop_watchdog, gemini_pool_lease_ttl`.
Тест `test_import_surface.py` перечисляет эти имена и проверяет `hasattr`. То же для `key_pool` (`gemini_pool, GEMINI_KEYS, gemini_model_name, KEY_LEASE_TTL`) и `telemetry` (`ATTEMPTS, JOB_STATS, betterstack_queue_size, _job_log`).

### 17.3 Тесты без тяжёлых зависимостей (G4)

- `requirements-dev.txt`: `-r requirements.txt`, `pytest`, `pytest-asyncio`, `httpx` (уже есть). Цель по умолчанию — CI с полным `requirements.txt`.
- Для быстрых юнит-тестов подсистемы `email_template/` (этапы E1–E2) **импорт `main`/`dddd_ocr` не нужен**: пакет `email_template` обязан импортироваться без `cv2`/`ddddocr` (нет импортов из `ocr_service.dddd_ocr` и `contact_sheet`). Тест `test_no_heavy_imports.py`: в подпроцессе `python -c "import ocr_service.email_template.validator"` не должен загружать `cv2`/`ddddocr` (`assert 'cv2' not in sys.modules`).
- Для API/job-тестов: `tests/conftest.py` при отсутствии `cv2`/`ddddocr` подставляет заглушки `sys.modules[...] = types.ModuleType(...)` **только если пакет реально не установлен** (`importlib.util.find_spec`). Тесты OCR-снимков (E0) запускаются только при настоящих пакетах (`pytest.importorskip`), иначе помечаются `skip` с понятной причиной, а в отчёте указывается, что снимки E0 не были сняты.

### 17.4 Таймаут вызова не превышает остаток дедлайна (G5)

В `gemini_runner.generate(deadline_ts, ...)` перед каждым вызовом:
```
remaining = deadline_ts - time.monotonic() - TEMPLATE_DEADLINE_MARGIN    # margin = 5 с
call_timeout = min(TEMPLATE_HARD_TIMEOUT, remaining)
если call_timeout < TEMPLATE_MIN_CALL_SECONDS (45): вызов не начинать → GenerationDeadline
```
`call_timeout` передаётся как `hard_timeout` в `call_gemini_generate`; read-timeout httpx = `min(TEMPLATE_HTTP_READ_TIMEOUT, call_timeout - 5)`. Попытка, сорванная дедлайном, **не считается** нарушением качества и не попадает в `attempts` как неудача валидации; в `attempts` пишется запись с `finish_reason="DEADLINE"`.
Новая переменная: `TEMPLATE_MIN_CALL_SECONDS` (45) и `TEMPLATE_DEADLINE_MARGIN` (5). Проверка согласованности: `MIN_ATTEMPT_SECONDS ≥ MIN_CALL_SECONDS + MARGIN`.

### 17.5 Порядок операций в `POST /template/submit` (G6)

Строго по шагам, без `await` между шагами 7–10:
1. Авторизация (`X-API-Key`) → пространство имён `ns` (17.6).
2. Валидация тела и белых списков (`400`).
3. `TEMPLATE_ENABLED`, ключи доступа, `TEMPLATE_MODELS`, наличие ключей Gemini (`503`).
4. Идемпотентность: живое задание по `(ns, account_id, client_request_id)` → ответ `reused:true`. **Ни история, ни счётчики не меняются.**
5. Breaker (`503`).
6. Лимиты: очередь → суточный счёт заданий → суточный счёт токенов (`429`). Отклонение пишет только `tpl_rejected` и `tpl_rejected_limit`.
7. Выбор брифа директором (с учётом `seed`/overrides).
8. Запись в историю директора.
9. Увеличение суточного счётчика заданий.
10. `JOBS[job_id] = ...` и `spawn_task`.

Отклонённый и переиспользованный submit **не** тратят историю и суточный счётчик (тест). Суточный счётчик заданий возврата не имеет (простота); токены считаются фактически.

### 17.6 Пространство имён идемпотентности (G7)

`ns = sha1(api_key)[:8]` (ключ не хранится и не логируется). Индекс идемпотентности: `(ns, account_id, client_request_id) → job_id`. `GET /template/result/{id}` дополнительно проверяет, что `job["ns"] == ns`, иначе `404` (чужое задание не отдаётся даже при знании `job_id`). Для `/preview` (HTTP Basic) проверка `ns` не применяется: оператор видит всё.

### 17.7 Что запрещено в логах (G8)

Помимо перечисленного в разделе 0: поле `where` и любые фрагменты HTML из `Issue`, тексты ремонтных сообщений, `concept`, `tail` ответа модели. В `tpl_validated` / `tpl_repair` пишутся только `rule_ids`, счётчики и `sha1`/`bytes`. Тест I11 расширяется: в stdout не должно быть ни одного значения `where` из отчёта.

### 17.8 Уточнения правил валидатора (конфликт «промпт главнее»)

Анализ `email_prompt.txt` показал места, где правило ТЗ строже промпта. Привести к промпту:

| Правило | Что менять | Причина |

| S07 | Обещания сроков: E только в блоке сообщения и индикаторе статуса; `в течение` / `через \d` вне этих блоков — W. «Завтра», «сегодня до», `за N часов/дней` остаются E везде | Промпт запрещает обещания сроков только в тестовом содержимом блока сообщения. «Скоро отправка» в индикаторе допустима |

| V08 | Для способов 8 и 15 (`$` после суммы / «USD») проверка идёт окном ±300 символов **в обе стороны**; позиция `$` не проверяется как «перед `{{price}}`» | Промпт требует `$` прямо перед `{{price}}`, но способ 8 ставит знак после суммы. Тесты: на каждое изменение — мутация, которая раньше падала как E и теперь проходит (или даёт W).

### 17.10 Прочее

- Все ответы `/template/*` получают поле `schema_version: 1`.
- `GET /template/result` добавляет `poll_after_ms` (рекомендуемая пауза: 4000 при `generating/repairing`, 2000 при `queued`, `null` при финальном статусе).
- `429` и `503` на `submit` содержат заголовок `Retry-After` (секунды).
- Лимит `TEMPLATE_SUBMIT_RATE_PER_MIN` (дефолт 20) на `X-API-Key` (скользящее окно, как у `/validate`) → `429`.
- Единая ветка семафора: `TEMPLATE_MAX_CONCURRENCY` при старте ограничивается `max(len(keys) - reserve, 1)` (предупреждение в лог).

## 18. Улучшения (Should), этап E9, каждое за флагом

Все пункты выключены или нейтральны по умолчанию. Включаются после замеров `eval_templates.py` на живом сервисе.

### 18.1 Подсказка про частые нарушения (`TEMPLATE_HINTS=1`, дефолт `0`)

Цель: поднять долю `valid` с первой попытки.
- Файл `email_template/hints.txt` — статический список 6–10 строк «частые ошибки» (например: «Прехедер: 50–110 символов и не меньше 3 пар `&nbsp;&zwnj;`»; «`{{productName}}` обязателен в `<title>` и в блоке деталей»; «Не пиши слова из запретного списка даже в отрицании»; «Каждый `<table>` с `role/cellpadding/cellspacing/border`»).
- Подсказка добавляется **в первое пользовательское сообщение**, системная инструкция остаётся дословной. `HINTS_VERSION` входит в `prompt_version` (`"1.0+h1"`).
- Содержимое составляется только по результатам `eval_templates.py` (топ-10 нарушаемых правил); не расширять без данных.
- Приёмка: A/B на 20 заданиях (с подсказкой и без). Включать, только если доля `valid` с первой попытки выросла.

### 18.2 Подсказка по контрасту в ремонте (`TEMPLATE_CONTRAST_SUGGEST=1`, дефолт `1`)

Для A01/A02 в ремонтное сообщение добавить **конкретный ближайший допустимый цвет**:
- `contrast.suggest_fix(fg, bg, target=4.5) -> Optional[str]`: сохраняя оттенок и насыщенность (HSL), двигать светлоту текста в сторону контраста с шагом 1% до `ratio ≥ 4.5`; если невозможно — менять светлоту фона; возвращать hex.
- Формулировка в ремонте: `- [A01] Контраст 3.2:1 (нужно 4.5:1). Замени цвет текста #8a8a8a на #767676 или темнее`. Всё равно решает модель, автофикс цвета не делаем (раздел 8.6).
- Тесты: `#8a8a8a` на `#ffffff` → результат с контрастом ≥ 4.5 и близкий оттенок; идемпотентность на уже допустимой паре (`None`).

### 18.3 Ремонт патчами (`TEMPLATE_REPAIR_MODE=full|patch`, дефолт `full`)

Цель: сократить время и токены ремонта (HTML 6–12 тыс. токенов возвращается целиком, патч требует лишь десятки токенов на правку).
- Режим `patch`: в ремонтном сообщении просить не весь файл, а блоки правок в формате:
  ```
  <<<ЗАМЕНА
  найти: <точная подстрока из твоего HTML>
  на: <новая подстрока>
  >>>
  ```
- Применение: каждый `найти` должен встретиться в текущем HTML **ровно один раз**; иначе правка отклоняется. Если применена хотя бы одна правка — повторная валидация; если ни одной или ответ не разобрался — **откат на режим `full`** в той же попытке (инфраструктурный ремонт, `n` не тратится).
- Не более 12 блоков, размер каждого `на` ≤ 2000 символов. Применение через `str.replace(..., count=1)` после проверки `count==1`; без `eval`/регулярок над HTML.
- В `attempts[i]` пишется `repair_mode: "full|patch|patch_fallback"`.
- Приёмка: на 20 заданиях сравнить среднюю длительность ремонта и долю `valid` с `full`; включать, если доля не упала, а время ремонта сократилось.

### 18.4 Фингерпринт разнообразия (`TEMPLATE_DIVERSITY_CHECK=1`, дефолт `0`)

Цель: ловить повторяющиеся тексты без ручного запуска eval.
- После валидации считается набор 5-грамм слов видимого текста и сохраняется (хэши 5-грамм, не текст) для последних `TEMPLATE_HISTORY` результатов.
- Жаккар > 0.5 с любым из последних → warning `D01` («схож с недавним письмом»), счётчик в `TEMPLATE_STATS`. Ремонт не запускается, результат не блокируется.
- Нужно как сигнал для тюнинга пулов и температуры.

### 18.5 Отмена задания (`POST /template/cancel/{job_id}`)

Для клиентов, которые отвалились по своему таймауту.
- Авторизация `X-API-Key` + проверка `ns`. Задание `pending/running` → `task.cancel()`, `status="error"`, `error="cancelled"`; финальное → `200` с текущим статусом без изменений; неизвестное → `404`.
- Ключ Gemini возвращается через `ensure_released` (I10). Токены, уже потраченные, учитываются.
- Отменённое задание не считается в breaker.

### 18.6 Классификация 429: RPM против суточной квоты

В `gemini_runner` разбирать `retryDelay` и `status` из тела ошибки:
- `retryDelay ≤ 120 с` → пара `(ключ, модель)` блокируется на `max(TEMPLATE_MODEL_COOLDOWN, retryDelay)`.
- `retryDelay > 120 с` или признак дневной квоты в сообщении (`per day`, `daily`) → пара блокируется до `TEMPLATE_QUOTA_BLOCK_SECONDS` (дефолт 900) и логируется `tpl_gemini_error` с `category="DAILY_QUOTA"`; если все пары цепочки заблокированы → задание `error` с кодом `quota` (не бесконечный цикл ожидания).
- Ничего из этого не затрагивает ключ целиком и OCR (I5).

### 18.7 Учёт кэшированных токенов и стоимость

- В `usage` добавить `cached` из `usageMetadata.cachedContentTokenCount`; в `attempts[i].tokens` поле `cached`. Системная инструкция (~5 тыс. токенов) повторяется во всех заданиях, неявное кэширование Gemini может сильно снизить стоимость; метрика покажет, работает ли оно с выбранной моделью.
- Опционально: `TEMPLATE_PRICE_IN_PER_MTOK` и `TEMPLATE_PRICE_OUT_PER_MTOK` (пусто = не считать). При заданных ценах `templates` в `/status.json` показывает `est_cost_24h`. Это оценка, а не бухгалтерия (как и `TEMPLATE_STATS`).
